## 1. 产品概述

### 1.1 产品定位

Live Platform 是一个面向跨境电商直播业务的**数据采集基础设施**，为派大星系统提供准确、实时的直播 GMV 数据支持，解放人工录入，提升数据时效性和准确性。

### 1.2 核心价值主张

**解放双手，再也无需招聘专门的实习生去录入各国家每日的数据；提高了数据时效性，辅助 BU 快速进行日度 PDCA；提高了数据的准确性，减少人为少录、错录导致的成本增加。**

### 1.3 业务背景

Livelab 主营业务围绕直播展开，每日产生大量的 GMV 数据。0331 前仍需手动录入三大渠道（TikTok、Shopee、Lazada）的 GMV 数据到 BPMS，才能计算对应业绩；BU 较难获取到准确的日度数据进行 PDCA，存在**耗时耗力、准确性低、时效性低**的痛点。

### 1.4 业务规模

- **TikTok**：160 个账号（核心平台）
- **Shopee**：60 个账号
- **Lazada**：5 个账号（新上线）

## 2. 用户与场景

### 2.1 目标用户

| 用户角色 | 使用频率 | 核心诉求 |
|---------|---------|---------|
| **爬虫采集工程师** | 每日多次 | 监控采集运行健康、排查异常、补采数据 |
| **数据团队** | 每日查看 | 确认今日数据完整性报告是否可用 |
| **BU 业务方** | 偶尔查看 | 了解直播间开播状态、数据采集进度 |

### 2.2 核心场景

#### 场景 1：录入直播间并监控开播

**角色：** BU 业务方  
**触发：** 新增直播间需要监控  
**流程：**
1. 用户在派大星系统录入直播间地址
2. 派大星调用 live-monitor API 获取直播间信息
3. live-monitor 开始监控该直播间是否开播
4. 检测到开播后（1分钟内），live-stream 自动拉取视频流
5. 视频流切割后推送到 OSS（防摸鱼）

**预期结果：** 直播间开播后 1 分钟内开始录制视频

#### 场景 2：用户登录授权

**角色：** BU 业务方  
**触发：** 需要采集某账号的商家后台数据  
**流程：**
1. 用户在派大星系统发起登录请求
2. adspower-server 创建浏览器环境并返回投屏 URL
3. 用户通过投屏界面手动登录
4. adspower-server 检测到登录成功，回调派大星系统
5. live-crawler 在下一轮调度任务中自动识别账号状态并开始采集

**预期结果：** 登录成功后，系统在下一轮调度任务中自动识别账号状态：
- 首次登录 → 执行全量采集
- 登出恢复 → 执行全量采集
- 正常状态 → 执行增量采集

详见 `.claude/references/logout-recovery-flow.md`

#### 场景 3：实时 GMV 数据采集

**角色：** 系统自动  
**触发：** 定时任务（5分钟）  
**流程：**
1. live-crawler 定时任务触发
2. 查询正在直播的账号列表
3. 执行双轨采集（TikTok/Shopee 浏览器，Lazada HTTP）
4. 采集到的原始数据推送到 Kafka
5. 数据仓库消费 Kafka 消息，清洗后推送到派大星系统

**预期结果：** 5 分钟内完成一轮实时采集

#### 场景 4：监控采集运行健康

**角色：** 爬虫采集工程师  
**触发：** 每日例行检查  
**流程：**
1. 工程师打开监控系统首页（端口 8777）
2. 监控系统读取 `monitor.db`，展示最近 30 分钟各国家各平台的运行健康
3. 发现某平台成功率下降，点击进入详情页
4. 查看 `account_sessions` 表中的异常记录（status != 'success'）
5. 根据 `error_message` 字段判断是登出、超时还是其他异常
6. 执行补采或排查问题

**数据来源：** 
- `account_sessions` 表：每次采集的执行记录
- `account_login_events` 表：登录状态变更事件
- `collection_events` 表：数据集采集明细

**预期结果：** 快速定位异常账号和原因，监控系统直接读库无需 API 中间层

#### 场景 5：确认今日数据完整性

**角色：** 数据团队  
**触发：** 每日下午确认数据是否可交付  
**流程：**
1. 数据团队打开监控系统首页
2. 查看今日完整性报告就绪度
3. 确认各国家各平台是否达到"已就绪"状态
4. 如有风险或阻塞，查看缺失数据集和受影响账号
5. 通知工程师补采

**预期结果：** 明确知道今日数据是否可用

- 四个上下文之间**无直接的串行依赖链**，是网状拓扑

### 4.4 数据采集 (live-crawler)

#### 4.4.1 核心功能

| 功能 | 优先级 | 说明 |
|------|--------|------|
| 双轨采集 | P0 | 浏览器（TikTok/Shopee）+ HTTP（Lazada） |
| 实时采集 | P0 | 5 分钟采集正在直播的场次 |
| 历史采集 | P0 | 每日全量采集 |
| 数据上报 | P0 | Kafka 推送原始数据 |
| 养号服务 | P0 | Cookie 定时刷新 |
| 采集完整性监控 | P1 | SQLite 记录采集事件 |

#### 4.4.2 采集模式

| 模式 | 触发条件 | 说明 |
|------|---------|------|
| 全量采集 | 新账号 / 登出恢复 | 采集所有历史数据 |
| 增量采集 | 正常状态 | 只采集最新数据 |
| 实时采集 | 定时任务（5分钟） | 只采集正在直播的场次 |

#### 4.4.3 平台差异矩阵

| 维度 | TikTok | Shopee | Lazada |
|------|--------|--------|--------|
| 采集方式 | 浏览器（DrissionPage） | 浏览器（DrissionPage） | HTTP API |
| 登录流程 | 扫码登录 + 投屏 | 自动点击已保存账号 | Cookie 直接注入 |
| 时区处理 | UTC | 国家本地时区（T-1） | UTC |
| 补采支持 | ✅ HTTP 重采集 | ❌ 仅浏览器 | ✅ HTTP 重采集 |
| 登出恢复 | 即时全量恢复 | 下轮增量（上轮数据完整） | 无需恢复（无登录） |

#### 4.4.4 登出恢复与补采机制

**核心规则详见：** `.claude/references/logout-recovery-flow.md`、`recrawl-http-spec.md`、`shopee-special-rules.md`

##### 登出恢复流程

| 平台 | 检测时机 | 恢复策略 | 数据完整性 |
|------|---------|---------|-----------|
| TikTok | 采集中途（`send_login_callback`） | 当轮切换全量采集 | 上一轮可能不完整 |
| Shopee | 采集开始前（`_check_login_status`） | 下轮全量采集 | 上一轮完整（已正常结束） |
| Lazada | 无需检测（HTTP 采集） | N/A | 始终完整 |

**TikTok 登出恢复逻辑：**
```python
# 采集中途检测到登出 → 立即切换全量模式
if login_callback_status == "success" and last_status == "logout":
    full_collection = True  # 当轮全量恢复
```

**Shopee 登出恢复逻辑：**
```python
# 采集开始前自动重登录 → 检测上一轮状态决定本轮模式
if _auto_relogin() and last_status == "logout":
    full_collection = True  # 下轮全量恢复
else:
    full_collection = False  # 正常增量
```

##### 补采机制

**触发条件：** 采集完整性监控检测到缺失数据（账号级/日期级/直播间级）

**补采支持矩阵：**

| 平台 | HTTP 补采 | 浏览器补采 | 补采规格 |
|------|----------|-----------|---------|
| TikTok | ✅ | ✅ | `.claude/references/recrawl-http-spec.md` |
| Shopee | ❌ | ✅ | 仅支持浏览器全量重采 |
| Lazada | ✅ | N/A | HTTP API 直接重试 |

**补采任务生命周期：**
```
缺失检测 → 创建补采任务 → 调度执行 → 状态更新 → 完整性验证
```

**补采优先级：**
1. P0：账号级缺失（live_list、replay_info）
2. P1：直播间级缺失（trend_gmv、trend_stats）
3. P2：日期级缺失（live_stats）

## 5. 统一监控系统

### 5.1 产品定位

**Live Platform 全链路监控面板**，为工程师提供直播间监控、视频流录制、数据采集三大模块的统一视图。

### 5.2 监控范围（分期实现）

#### Phase 1：数据采集监控（当前实现）
- ✅ live-crawler 采集运行健康
- ✅ 数据完整性报告就绪度
- ✅ 登录状态追踪
- ✅ 补采任务管理

#### Phase 2：视频流录制监控（待实现）
- ⏳ 推流健康度（断流次数、重连成功率）
- ⏳ 视频切割上传成功率
- ⏳ OSS 上传延迟
- ⏳ 当前录制房间数

#### Phase 3：直播间监控（待实现）
- ⏳ 开播检测时效（1分钟内检测率）
- ⏳ 房间分配成功率
- ⏳ 主备切换状态
- ⏳ WebSocket 连接数

### 5.3 核心问题（Phase 1）

1. 最近 15/30/60 分钟，当前国家与平台的采集运行是否健康？
2. 今天这份"数据采集完整性报告"是否已经达到可查看、可交付的状态？

### 5.4 技术架构（Phase 1）

```
┌─────────────────────────────────────────┐
│  Vue3 监控前端 (port 8777)              │
│  - 国家级采集驾驶舱                      │
│  - 完整性报告就绪度                      │
└──────────────┬──────────────────────────┘
               │ 直接读库（无 API 写入层）
               ▼
┌─────────────────────────────────────────┐
│  SQLite: monitor.db                     │
│  - account_sessions (采集执行记录)       │
│  - collection_events (数据集明细)        │
│  - account_login_events (登录状态)       │
│  - recrawl_tasks (补采任务)              │
└──────────────▲──────────────────────────┘
               │ 直接写入
┌──────────────┴──────────────────────────┐
│  live-crawler 采集进程                   │
│  - CollectionTracker 写入 sessions       │
│  - registry.py 写入 collection_events    │
│  - login_status_manager 写入 login_events│
└─────────────────────────────────────────┘
```

**架构优势：**
- 监控与采集解耦，监控故障不影响采集
- 前端直接读库，无需维护 API 写入层
- 数据模型清晰，易于扩展新指标

**Phase 2/3 扩展方向：**
- live-stream 和 live-monitor 各自维护独立 monitor.db
- 前端聚合查询多个数据源
- 或迁移到共享监控数据库（待技术方案评估）

```
│     ├─ Shopee 平台块
│     └─ Lazada 平台块
└─ 下半区：今日完整性报告就绪度
   └─ 国家卡片
      ├─ TikTok 平台块
      │  ├─ 状态：已就绪 / 有风险 / 已阻塞
      │  ├─ 缺失数据集数
      │  └─ 受影响账号数
      ├─ Shopee 平台块
      └─ Lazada 平台块
```

### 5.6 监控指标定义（Phase 1）

#### 5.6.1 运行健康指标

| 指标 | 定义 | 阈值 |
|------|------|------|
| 成功率 | 窗口内 success 次数 / 总次数 | 绿色 ≥95%，黄色 ≥80%，红色 <80% |
| P95 耗时 | 窗口内 95 分位耗时 | - |
| 异常账号数 | 窗口内出现非 success 的账号数 | - |
| 最近异常时间 | 窗口内最后一条异常记录时间 | - |

#### 5.6.2 报告就绪度指标

| 状态 | 定义 |
|------|------|
| 已就绪 | 所有关键数据集覆盖率 ≥95% |
| 有风险 | 所有关键数据集覆盖率 ≥80%，且至少一个 <95% |
| 已阻塞 | 任一关键数据集覆盖率 <80% |

## 7. 数据流

### 7.1 端到端数据流

```
派大星系统录入直播间
    ↓
live-monitor 监控开播
    ↓
live-stream 拉取视频流 → OSS 存储 → Kafka 通知
    ↓
用户登录授权（adspower-server）
    ↓
live-crawler 采集 GMV 数据 → Kafka 推送
    ↓
数据仓库消费 Kafka → 清洗计算
    ↓
派大星系统展示数据
```

### 7.2 Kafka Topic 设计

| Topic | 生产者 | 消费者 | 说明 |
|-------|--------|--------|------|
| `liveTs` | live-stream | 数据仓库 | 视频切片上传通知 |
| `streamer_lazada_relate_data` | live-crawler | 数据仓库 | Lazada 采集数据 |
| `streamer_tiktok_relate_data` | live-crawler | 数据仓库 | TikTok 采集数据 |
| `streamer_shopee_relate_data` | live-crawler | 数据仓库 | Shopee 采集数据 |

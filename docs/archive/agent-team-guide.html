Agent Team 使用指南

live-platform-squad · 5 人协作团队 · 按需激活，不走流水线

1. 什么是 Agent Team？

一句话解释：Agent Team 是一组 AI 协作成员，每个成员有不同的专长，由你（通过 team-lead）按需调度来完成复杂任务。

你可以把它想象成一个虚拟开发小组——有人负责质疑方向、有人负责调研方案、有人负责规划步骤、有人负责架构设计、有人负责代码审查。你是这个小组的 leader，决定什么时候叫谁上场。

关键点：

• 不是所有任务都需要全员出动，简单任务可能只需要 1-2 个成员

• 成员之间不会自动交接，都是向你（team-lead）汇报

• 团队按需创建，用完即解散，不占常驻资源

2. 团队成员

⚡
Challenger — 质疑专家
找盲点、提反方案、追问假设。在你准备做大决策前，让他先泼一盆冷水，避免方向性错误。有几个盲点说几个，不凑数。
🔭
Scout — 侦察专家
扫描本地代码现状 + 搜索 GitHub 成熟方案。告诉你「现在是什么样」和「外面有什么更好的」，帮你做自研 vs 复用的决策。
📋
Planner — 规划专家
把复杂任务拆成可执行的分阶段计划。明确每步做什么、依赖什么、怎么验收。适合多步骤、多文件的大任务。
🏛️
Architect — 架构专家
做技术选型和架构设计。给出方案对比、选型理由、架构图和接口契约。遵循项目的 DDD 架构决策。
✅
Reviewer — 审查专家
代码合并前的质量把关。按 P0/P1/P2 分级报告问题，检查安全漏洞。P0 问题直接阻断合并，没有例外。

3. 如何启动团队

在 Claude Code 对话中直接说：

> 启动团队

Claude 会读取 ~/.claude/teams/live-platform-squad/config.json，然后并行启动 5 个成员。全员就位后会逐一报到。

注意：团队是按需创建的（on-demand）。任务完成后会自动解散。下次需要时再说「启动团队」即可重建。不需要手动管理生命周期。

启动后你会看到类似这样的消息：

⚡ challenger — 已就位，等待任务
🔭 scout — 已就位，等待任务
📋 planner — 已就位，等待任务
🏛️ architect — 已就位，等待任务
✅ reviewer — 已就位，等待任务

4. 工作流程

核心原则：你是 team-lead，按任务复杂度决定叫谁上场。没有固定流水线，不要求每个任务都走完全部角色。

调度模式：

• 所有成员完成工作后，统一向你（team-lead）汇报

• 你看完汇报后，决定下一步交给谁、或者自己动手

• 成员之间不会自动交接——你是唯一的调度中心

你可以这样指挥成员：

> @challenger 帮我看看这个需求有没有盲点：[需求描述]

> @scout 调研一下 Python 里有什么成熟的任务调度库

> @planner 把这个功能拆成实施计划

> @architect 设计一下这两个服务之间的接口

> @reviewer 审查一下当前的代码变更

5. 实际使用场景

场景 A：简单 Bug 修复
你修 bug → @reviewer 审查 → 合并

不需要质疑、不需要调研、不需要规划。直接修完让 reviewer 过一眼就行。

场景 B：新功能开发
@challenger 质疑需求 → @scout 调研方案 → @planner 出计划 → @architect 设计 → 你实现 → @reviewer 审查

大功能走完整流程，确保方向正确、方案成熟、计划可执行。

场景 C：技术调研
@scout 调研 → 你决策

只需要 scout 出去看看外面有什么方案，回来给你报告。

场景 D：架构决策
@challenger 质疑假设 → @architect 出方案对比 → 你拍板

先让 challenger 帮你想清楚问题，再让 architect 给出技术方案。

场景 E：重构计划
@scout 扫描现状 → @planner 出分阶段计划 → @challenger 复审计划 → 你执行

重构需要先摸清现状，再规划步骤，最后让 challenger 检查计划有没有遗漏。

灵活组合：以上只是典型场景，你可以根据实际情况自由组合。觉得不需要某个角色就跳过，觉得需要额外质疑就多叫一次 challenger。

6. 门控机制

团队有 3 个门控节点，但只有 1 个是强制的：

门控负责人性质什么时候用
审查门 ✅ reviewer 强制 代码合并前必须过。P0 阻断合并。
需求门 ⚡ challenger 按需 大变更、方向性决策时激活
方案门 ⚡ challenger 按需 复杂方案完成后，让 challenger 复审

为什么只有 reviewer 是强制的？

因为代码质量和安全是底线，不能跳过。而需求质疑和方案复审，对于简单任务来说是过度设计——一个 3 行的 bug fix 不需要先被质疑一遍。

P0/P1/P2 严重度说明：

• P0 — 阻断合并：安全漏洞、数据丢失、服务崩溃

• P1 — 必须修复：性能问题、设计缺陷

• P2 — 建议改进：可读性、代码风格

7. 常见问题

Q：团队启动后我可以不用某个成员吗？

可以。成员启动后只是待命状态，你不 @他 就不会消耗资源。

Q：我可以同时给多个成员派任务吗？

可以。比如让 scout 调研的同时让 challenger 质疑需求，他们会并行工作。

Q：成员的回复太长/太短怎么办？

直接告诉他。比如「简短一点，只给结论」或「展开说说第 2 点」。成员会调整。

Q：团队配置文件在哪？

~/.claude/teams/live-platform-squad/config.json 是团队配置，prompts/ 目录下是每个成员的 prompt 文件。你可以直接编辑来调整行为。

## 三、跨服务边界规则

### 3.1 根 docs/ 放什么

| 类型 | 内容 | 示例 |
|------|------|------|
| `docs/specs/` | 跨服务接口规范、产品需求文档（PRD）、全局数据模型 | PRD-live-platform-v1.0.md |
| `docs/designs/` | 跨服务架构设计、全局技术决策（ADR）、系统级方案 | live-platform-architecture.md、mediamtx-deployment-adr.md |
| `docs/plans/` | 跨服务实施计划、全局里程碑 | architecture-simplification-plan.md |
| `docs/archive/` | 已完成/被取代的全局文档 | 历史审计报告、旧版设计 |
| `docs/superpowers/` | Superpowers Skill 生成的 plans/specs（按需创建） | 由 Skill 自动管理 |

### 3.2 services/*/docs/ 放什么

| 类型 | 内容 | 示例 |
|------|------|------|
| `specs/` | 该服务独有的接口规范、对接文档、数据样本 | lazada-http-crawler-spec.md、shopee-数仓对接文档.md |
| `designs/` | 该服务独有的技术方案 | lazada-login-state-detection.md |
| `plans/` | 该服务独有的实施计划 | （按需创建） |
| `archive/` | 该服务已完成的历史文档 | MIGRATION_SUMMARY.md |

### 3.3 判断边界的决策树

```
文档涉及几个服务？
├── 1 个 → 放该服务的 docs/ 下
├── 2+ 个 → 放根 docs/ 下
└── 0 个（纯工具/流程） → 放 .claude/docs/ 或根 docs/ 下
```

### 3.4 禁止事项

- 禁止在服务 docs/ 中放跨服务设计（违反单一权威源）
- 禁止在根 docs/ 中放单服务独有规范（增加噪音）
- 跨服务的 Superpowers 产出必须放根 `docs/superpowers/`（回应 DA#4：服务级 `docs/superpowers/` 允许存在，但仅限该服务独有的 Skill 产出）

## 四、Superpowers 策略（回应 DA#4）

### 4.1 核心原则

**不要每服务都预建 superpowers/ 目录，按需由 Skill 生成。**

### 4.2 具体规则

1. **默认位置**：Superpowers Skill 生成的跨服务文档放 `docs/superpowers/`（根级别）
2. **服务级允许**：若 Skill 产出仅涉及单一服务，允许放在 `services/X/docs/superpowers/`（回应 DA#4：与 §3.3 决策树一致——1 个服务的文档放该服务 docs/ 下）
3. **按需创建**：superpowers 目录（无论根级还是服务级）仅在 Skill 首次产出时创建，不预建空目录
4. **内部结构**：由 Superpowers Skill 自行管理（通常为 `plans/` 和 `specs/`），不强制并入四类标准目录
5. **过期处置**：superpowers 产出过期后，按正常归档流程移入对应层级的 `archive/`

### 4.3 与四类目录的关系

```
docs/
├── specs/          ← 人工维护的规范
├── designs/        ← 人工维护的设计
├── plans/          ← 人工维护的计划
├── archive/        ← 历史文档
└── superpowers/    ← Skill 自动生成（独立体系，不混入上述四类）
    ├── plans/
    └── specs/
```

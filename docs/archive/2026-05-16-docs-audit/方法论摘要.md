## 问题 a：paths frontmatter 的 glob 语法与最佳粒度

**来源**：`topics/claude-md-mechanisms.md` § 三、`.claude/rules/` 路径作用域机制

### 结论

**最佳粒度原则**：
- **具体扩展名优先**：`src/api/**/*.ts` 比 `src/api/**/*` 更精确，避免误触发
- **双星号 `**` 用于跨目录递归**：`**/*.test.ts` 匹配所有层级的测试文件
- **花括号展开多扩展名**：`**/*.{ts,tsx}` 比分行写两条规则更简洁
- **避免过宽的根匹配**：`**/*` 会对所有文件触发，应改为 `src/**/*` 或 `**/*.ext`

**实操建议**：
- 单文件类型规则（如 SQL）：`**/*.sql`
- 特定目录规则（如 API）：`src/api/**/*.ts`
- 多扩展名规则（如前端）：`src/components/**/*.{tsx,css}`
- 测试文件规则：`**/*.{test,spec}.{ts,tsx,js}`

**适用场景**：编码规范、测试约束、安全审查等"文件类型维度"的规则。

## 问题 b：子目录 CLAUDE.md 的懒加载机制与 @import 时机

**来源**：`topics/claude-md-mechanisms.md` § 二、加载机制

### 结论

**懒加载 vs 强制加载的决策矩阵**：

| 场景 | 选择 | 理由 |
|------|------|------|
| 模块级背景知识（如 API 设计、前端组件规范） | 懒加载 | 仅当读该模块文件时触发，节省 token |
| 全局必读的架构说明 | @import | 启动时立即展开，确保所有 Agent 都知道 |
| 可选的参考文档 | 懒加载 + 自然语言指引 | 在根 CLAUDE.md 用"按需读取"列表引导 |
| 跨模块共享的规则（如安全审查） | 无 paths 的 rules 文件 | 启动时无条件加载，等价于根 CLAUDE.md |

**@import 的三个使用原则**：
1. **递归深度不超过 3 层**：`@import src/api/CLAUDE.md` 可以，`@import src/api/v1/v2/v3/CLAUDE.md` 不行
2. **只 import 真正全局的模块**：如果某个子目录 CLAUDE.md 只有 5% 的任务会用到，不值得 import
3. **import 后在根文件中标注**：`@import src/api/CLAUDE.md  # API 模块设计背景`，便于维护者理解

**懒加载的触发方式**：
- 自然触发：Claude 读取该目录的任何文件时自动加载
- 主动触发：在对话中指示 Claude "请读 src/api/CLAUDE.md"
- 不建议用 `--add-dir` 环境变量，因为不可版本控制

**适用场景**：monorepo 中各服务有独立 CLAUDE.md 时，根文件只 import 架构总览，其他模块规则保持懒加载。

## 问题 c：单 CLAUDE.md 的合理行数上限与拆分阈值

**来源**：`topics/claude-md-mechanisms.md` § 五、最佳实践 + `topics/claude-md-guide.md`

### 结论

**行数上限与遵从度关系**：
- **< 60 行**：最优遵从度，Claude 理解准确率 > 95%
- **60-200 行**：可接受，遵从度开始下降，但仍可维持 > 80%
- **200-400 行**：明显下降，遵从度 60-80%，开始出现"越用越蠢"现象
- **> 400 行**：严重衰减，遵从度 < 60%，且推理成本增加 20%+（ETH Zurich 研究）

**拆分阈值与触发条件**：

| 行数 | 状态 | 行动 |
|------|------|------|
| < 60 | 健康 | 保持 |
| 60-150 | 可控 | 监控，准备拆分 |
| 150-200 | 警告 | 立即拆分 |
| > 200 | 危险 | 必须拆分 |

**拆分策略（三步法）**：
1. **根文件做薄**：保留全局约束（命名规范、提交规范、文档地图），删除所有条件性规则（"如果……则……"）
2. **规则按关注点拆 `.claude/rules/`**：按文件类型（`typescript.md`、`testing.md`）或模块（`frontend/react.md`）拆分，配合 `paths` frontmatter
3. **用 `/memory` 逐条验收**：每删一条规则，运行 `/memory` 确认 session 加载链路仍完整

**实战案例**：从 200+ 行压到 60 行以内，反而避免了文件膨胀导致的遵从度下降。

**适用场景**：所有项目，特别是 monorepo 和团队协作项目。

## 问题 d：单一权威源在 monorepo 中的实操边界

**来源**：`topics/claude-md-mechanisms.md` § 一、文件层级与作用域 + 项目 CLAUDE.md 规则

### 结论

**分工原则**：

| 层级 | 内容 | 共享方式 | 修改权限 |
|------|------|----------|----------|
| **根 CLAUDE.md** | 架构总览、全局命令、文档地图、提交规范 | git 提交 | 团队共同维护 |
| **子项目 CLAUDE.md** | 模块特有背景、API 设计、组件规范 | git 提交 | 模块 owner 维护 |
| **`.claude/rules/`** | 技术约束、编码规范、安全审查 | git 提交 | 技术委员会维护 |
| **`.claude/CLAUDE.md`** | 补充说明、工作流指引 | git 提交 | 可选，通常空 |
| **`CLAUDE.local.md`** | 个人沙箱 URL、测试数据 | .gitignore | 个人维护 |

**禁止复制副本的实操**：
- ❌ 在根 CLAUDE.md 和 `src/api/CLAUDE.md` 中都写"API 规范"
- ✅ 根 CLAUDE.md 只写"API 规范详见 src/api/CLAUDE.md"，或用 @import 强制加载

**子项目 CLAUDE.md 的层级继承**：
- 不重复根 CLAUDE.md 的通用规则（如提交规范、命名约定）
- 仅记录子项目特有约束（如"API 返回必须包含 request_id"）
- 可引用根文件的规则："遵循根 CLAUDE.md 的提交规范，另外……"

**monorepo 推荐结构**：
```
project/
├── CLAUDE.md                    ← 全局：架构、build 命令、文档地图
├── services/
│   ├── live-monitor/
│   │   └── CLAUDE.md            ← 模块级：监控特有规范（懒加载）
│   ├── live-stream/
│   │   └── CLAUDE.md            ← 模块级：流录制特有规范（懒加载）
│   └── live-crawler/
│       └── CLAUDE.md            ← 模块级：采集特有规范（懒加载）
└── .claude/
    ├── rules/
    │   ├── python.md            ← paths: **/*.py
    │   ├── testing.md           ← paths: **/*.test.py
    │   └── global-style.md      ← 无 paths：全局风格
```

**适用场景**：所有 monorepo 项目，特别是 4+ 个子项目的大型整合。

## 问题 e：多 Agent 协作时哪些治理动作适合程序化校验

**来源**：`topics/agent-team-architecture.md` § 二、Mavis 架构 + § 五、四条纪律

### 结论

**程序化校验 vs 自然语言约束的决策矩阵**：

| 治理动作 | 程序化校验 | 自然语言约束 | 理由 |
|---------|----------|-----------|------|
| **代码风格检查** | ✅ | ❌ | 确定性规则，linter 比 prompt 可靠 |
| **提交前验证** | ✅ | ❌ | 必须 100% 触发，不能依赖 AI 判断 |
| **文件路径作用域** | ✅ | ❌ | glob 匹配确定性强，paths frontmatter 是标准做法 |
| **重试上限** | ✅ | ❌ | 防止死循环，需要硬编码的计数器 |
| **Worker-Verifier 对掐** | ✅ | ❌ | 两个 AI 的调度必须由 Engine 中转，不能靠 prompt 协调 |
| **架构说明** | ❌ | ✅ | 需要语义理解，自然语言更灵活 |
| **业务规则** | ❌ | ✅ | 变化频繁，硬编码成本高 |
| **文档地图** | ❌ | ✅ | 按需读取，自然语言指引更合适 |
| **角色分工** | ⚠️ | ✅ | 可用 CLAUDE.md 约束，但 Agent 工具集分工需程序化 |

**三条可操作的纪律**：

1. **写的不审，审的不写**
   - 程序化实现：在 `.claude/rules/` 中配置 Reviewer Agent 的权限，禁止访问 Writer 的工作目录
   - 自然语言补充：在 CLAUDE.md 中说明"审校 Agent 只看最终产出文件"

2. **真正的分工是工具集分工**
   - 程序化实现：给不同 Agent 配不同的 skill、不同的工作目录、不同的权限级别
   - 自然语言补充：在 CLAUDE.md 中说明各 Agent 的职责边界

3. **验证嵌入生产，不是事后跑**
   - 程序化实现：在 Team Engine 中硬编码 verify-retry 循环，每步产出立刻挑
   - 自然语言补充：在 teamcreate prompt 中写"each agent must review previous agent's output before proceeding"

**适用场景**：
- 程序化校验：所有涉及确定性、可重复、必须 100% 触发的治理
- 自然语言约束：所有涉及语义、变化频繁、可容错的治理

## 反例条款：应避免的做法

### ❌ 反例 1：过度 @import

**错误做法**：
```markdown
# 根 CLAUDE.md
@import src/api/CLAUDE.md
@import src/frontend/CLAUDE.md
@import src/database/CLAUDE.md
@import src/auth/CLAUDE.md
@import src/utils/CLAUDE.md
```

**问题**：
- 启动时全部展开，token 消耗翻倍
- 大多数任务只需要其中 1-2 个模块，其他都是噪音
- 遵从度反而下降（ETH 研究）

**正确做法**：
- 只 @import 架构总览级别的文件（如 `src/api/CLAUDE.md` 如果是全局 API 设计）
- 其他模块保持懒加载，在根文件用自然语言指引："需要了解 API 设计时读 src/api/CLAUDE.md"

---

### ❌ 反例 2：单 CLAUDE.md 超过 200 行

**错误做法**：
```markdown
# CLAUDE.md（400+ 行）
## 全局规范
## Python 规范
## TypeScript 规范
## 测试规范
## 数据库规范
## API 规范
## 前端规范
## 安全规范
## 提交规范
## 文档规范
```

**问题**：
- 遵从度 < 60%，推理成本增加 20%+
- Claude 无法同时记住所有规则，后面的规则被忽视
- 维护成本高，改一条规则要改整个文件

**正确做法**：
- 根文件 < 60 行，只保留全局约束
- 其他规则拆到 `.claude/rules/` 中，配合 `paths` frontmatter

---

### ❌ 反例 3：paths frontmatter 过宽

**错误做法**：
```yaml
---
paths:
  - "**/*"
---
# 这条规则对所有文件都生效
```

**问题**：
- 每次读任何文件都加载这条规则，噪音太大
- 无法区分不同文件类型的需求

**正确做法**：
```yaml
---
paths:
  - "**/*.ts"
  - "**/*.tsx"
---
# 只对 TypeScript 文件生效
```

---

### ❌ 反例 4：子项目 CLAUDE.md 复制根文件内容

**错误做法**：
```markdown
# services/live-crawler/CLAUDE.md
## 提交规范
- 使用 git commit -m "type: message"
- 遵循 Conventional Commits

## 命名约定
- 变量用 snake_case
- 类用 PascalCase

## API 规范
- 返回统一错误格式
```

**问题**：
- 与根 CLAUDE.md 重复，维护两份
- 如果根文件改了，子文件容易遗漏
- 违反"单一权威源"原则

**正确做法**：
```markdown
# services/live-crawler/CLAUDE.md
遵循根 CLAUDE.md 的提交规范、命名约定、API 规范。

## 采集特有规范
- 采集模式分为 realtime / full / once
- 登出恢复流程详见 docs/logout-recovery-flow.md
```

---

### ❌ 反例 5：用自然语言约束替代程序化校验

**错误做法**：
```markdown
# CLAUDE.md
## 提交前必须运行测试
请在每次提交前运行 `npm test`，确保所有测试通过。
```

**问题**：
- 依赖 AI 的判断，不可靠
- 无法强制执行，AI 可能忘记
- 无法追踪是否真的运行了

**正确做法**：
- 用 git hook（pre-commit）强制运行测试
- 在 CLAUDE.md 中说明："提交前的测试由 git hook 自动运行，无需手动"
- 如果是 Agent 协作，在 Team Engine 中硬编码验证步骤

---

### ❌ 反例 6：monorepo 中没有子项目 CLAUDE.md

**错误做法**：
```
project/
├── CLAUDE.md                    ← 400+ 行，包含所有子项目规范
├── services/
│   ├── live-monitor/
│   ├── live-stream/
│   └── live-crawler/
```

**问题**：
- 根文件膨胀，遵从度下降
- 无法区分各子项目的特有约束
- 新人不知道哪些规则适用于哪个模块

**正确做法**：
```
project/
├── CLAUDE.md                    ← 60 行，全局架构
├── services/
│   ├── live-monitor/
│   │   └── CLAUDE.md            ← 模块特有规范
│   ├── live-stream/
│   │   └── CLAUDE.md
│   └── live-crawler/
│       └── CLAUDE.md
└── .claude/rules/               ← 技术约束
```

## 总结表

| 问题 | 核心结论 | 可执行指标 |
|------|---------|----------|
| **a. paths 粒度** | 具体扩展名优先，`**` 用于递归 | `src/api/**/*.ts` 而非 `**/*` |
| **b. 懒加载时机** | 模块规范懒加载，架构说明 @import | 根文件 @import < 3 个，其他懒加载 |
| **c. 行数上限** | < 60 行最优，> 200 行必须拆 | 超 150 行立即拆分 |
| **d. monorepo 分工** | 根文件全局，子文件模块特有 | 禁止复制副本，用路径引用 |
| **e. 程序化校验** | 确定性规则程序化，语义规则自然语言 | 提交验证、路径作用域必须程序化 |

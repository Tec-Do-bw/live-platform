## 反对意见 1：7 个文件移动的 ROI 不成立——过度改造

**反驳点**：《整顿方案.md》第一节「文件移动清单」提议移动 7 个文件。

**具体质疑**：

- 3 个根 docs/ 顶层散文件（DDD、PRD、architecture-review）自 2026-05-03 至 05-10 创建以来，从未因「找不到」或「放错位置」导致过任何实际问题。现状报告将其标为 P0，但 P0 应保留给「阻碍工作」的问题，而非「不够整齐」。
- 3 个 superpowers 文件（2026-03-31）已过期近 2 个月，无人引用、无人阅读。移动它们到 `docs/archive/` 与直接留在原地的实际差异为零——都是死文档。
- `docs/guides/agent-team-guide.html` 同理，一次性产物，移动它不解决任何痛点。

**援引依据**：《方法论摘要.md》反例条款 3「paths frontmatter 过宽」的底层逻辑——做改动的前提是存在真实痛点，而非追求形式整齐。同时参照第 c 条拆分策略的精神：「超 150 行立即拆分」是因为遵从度下降，而非因为行数本身不好看。类比到文件移动：移动的理由应是「放错位置导致了具体问题」，而非「不符合四类目录约定」。

**建议替代方案**：
- 仅移动 3 个根 docs/ 顶层散文件（真正违反四类约定且可能被后续文档混淆）。
- superpowers 3 个文件 + guides HTML：原地保留，不花工程时间。如果未来有人需要清理，在 `docs/archive/` 的 README 中加一行「历史 superpowers 文件仍在 services/live-crawler/docs/superpowers/，已过期」即可。
- 将 7 文件移动缩减为 3 文件移动，ROI 从「7 次 git mv + 2-4 处引用更新」降为「3 次 git mv + 1 处引用更新」。

## 反对意见 2：`read-before-write.md` 新增 Dockerfile/docker-compose glob 过度触发

**反驳点**：《rules-改造方案.md》第一节 §1 提议为 `read-before-write.md` 新增 `services/**/Dockerfile` 和 `services/**/docker-compose*.yml`。

**具体质疑**：

- `read-before-write.md` 的规则正文是「编辑前必读子项目 CLAUDE.md」。但 Dockerfile 和 docker-compose.yml 的修改场景通常是运维/部署调整，此时需要的上下文是部署文档（`docs/specs/deployment-guide.md`），而非子项目 CLAUDE.md（记录的是代码架构约束）。
- 触发规则后 Claude 会去读 CLAUDE.md，但 CLAUDE.md 中并无 Docker 相关约束信息。这是一次「加载了但没用」的 token 浪费。
- 当前项目中 Dockerfile 仅存在于 `services/live-platform/`（Phase 1 新增），其他 4 个服务尚无 Dockerfile。为 1 个文件新增 glob 的收益极低。

**援引依据**：《方法论摘要.md》第 a 条「避免过宽的根匹配」+ 反例条款 3「paths frontmatter 过宽——每次读任何文件都加载这条规则，噪音太大」。虽然此处不是 `**/*`，但新增的 glob 匹配的文件与规则正文的行动指令（读 CLAUDE.md）之间缺乏因果关系，属于「触发了但无法产生有效行动」的过度触发。

**建议替代方案**：
- 不新增 Dockerfile/docker-compose glob。
- 如果确实需要「编辑部署配置前先读上下文」，应新建一条独立规则（如 `read-deployment-docs-before-edit.md`），paths 匹配 `**/Dockerfile` + `**/docker-compose*.yml`，正文指向 `docs/specs/deployment-guide.md` 而非 CLAUDE.md。

## 反对意见 3：根 CLAUDE.md「上下文按需加载指引」表格违反单一权威源

**反驳点**：《rules-改造方案.md》第二节提议在根 CLAUDE.md 末尾新增一个 9 行表格「上下文按需加载指引」。

**具体质疑**：

根 CLAUDE.md 第 87-101 行已有「IMPORTANT: 工作流规则」段，其中第 89-96 行的表格已经描述了 4 条 rules 的触发条件和核心要求。新增的「上下文按需加载指引」表格与之存在以下重叠：

| 新表格行 | 既有内容 | 重叠点 |
|----------|---------|--------|
| 「编辑某服务代码 → services/X/CLAUDE.md → 自动（懒加载）」 | 工作流规则表第 1 行：`read-before-write.md` 触发条件「编辑 services/*/ 下文件时」 | 同一场景的两种表述 |
| 「修改文档 → 根 CLAUDE.md 文档管理规则段 → 自动（single-source-of-truth rule）」 | 工作流规则表第 4 行：`single-source-of-truth.md` 触发条件「创建/编辑文档时」 | 同一场景的两种表述 |

这违反了项目自身的 `.claude/rules/single-source-of-truth.md` 规则：「每份技术文档只在一个位置维护，禁止复制副本」。新表格本质上是对 rules 触发机制的第二份描述。

**援引依据**：
- 《方法论摘要.md》反例条款 4「子项目 CLAUDE.md 复制根文件内容——与根 CLAUDE.md 重复，维护两份」。虽然此处不是子项目复制根，而是根内部两个段落描述同一件事，但违反的原则相同。
- 《方法论摘要.md》第 c 条「< 60 行最优，> 200 行必须拆」。根 CLAUDE.md 当前 113 行，新增表格约 20 行后达到 133 行，进入「可控但需监控」区间。每一行新增都应有不可替代的价值。

**建议替代方案**：
- 不在根 CLAUDE.md 新增表格。
- 将「上下文按需加载指引」作为独立文件放在 `.claude/docs/context-loading-guide.md`，根 CLAUDE.md 仅加一行引用：「上下文加载策略详见 `.claude/docs/context-loading-guide.md`」。
- 这样既保留了指引内容，又不膨胀根文件，且遵守单一权威源。

## 反对意见 4：Superpowers「一刀切」禁止服务级目录过于武断

**反驳点**：《整顿方案.md》第四节 §4.2 第 4 条：「任何 `services/*/docs/superpowers/` 均视为违规，应迁移至根 `docs/superpowers/` 或归档」。

**具体质疑**：

- 根 CLAUDE.md 第 112 行的 Superpowers 例外原文是：「根 `docs/superpowers/` 沿用 Superpowers Skill 体系生成的 plans/specs，不强制并入上述四类」。这条规则定义了 Superpowers 文档的存放位置，但并未明确禁止服务级 superpowers 目录。
- Superpowers Skill 的工作模式是「在当前工作目录生成文档」。如果用户在 `services/live-crawler/` 目录下调用 Superpowers Skill，Skill 会自然地在该目录下生成 `docs/superpowers/` 结构。强制要求所有 Superpowers 产出集中到根目录，等于要求用户每次调用 Skill 后手动移动文件，增加了操作摩擦。
- 当前 3 个 superpowers 文件确实已过期，但「过期」和「位置违规」是两个独立问题。归档的理由应是「过期」，而非「位置错误」。

**援引依据**：《方法论摘要.md》第 d 条「monorepo 分工」的判断边界——「文档涉及几个服务？1 个 → 放该服务的 docs/ 下」。这 3 个 superpowers 文件全部是 shopee 相关（live-crawler 独有业务），按跨服务边界规则应放在服务级 docs/ 下。整顿方案自身的 §3.3 决策树与 §4.2 第 4 条存在内部矛盾。

**建议替代方案**：
- 将 §4.2 第 4 条修改为：「服务级 `docs/superpowers/` 允许存在，但仅限该服务独有的 Skill 产出。跨服务的 Superpowers 产出放根 `docs/superpowers/`」。
- 当前 3 个过期文件的处置理由改为「已过期归档」，而非「位置违规」。

## 反对意见 5：`single-source-of-truth.md` 新增 `**/CLAUDE.md` 是语义噪音

**反驳点**：《rules-改造方案.md》第一节 §4 提议为 `single-source-of-truth.md` 新增 `**/CLAUDE.md` glob。

**具体质疑**：

- 方案自身承认「`**/*.md` 已包含 CLAUDE.md，此条为语义强调」，最终建议「保持现状不变」。但方案的行文结构（先提出改造 → 再自我否定）造成了阅读混乱。
- 更重要的是：如果未来有人只看 paths 列表而不读正文分析，可能会误以为需要加上这条。这种「提出又撤回」的写法在执行文档中是噪音。

**援引依据**：《方法论摘要.md》第 a 条「具体扩展名优先」的精神——glob 列表应精确且无冗余。一个被 `**/*.md` 完全覆盖的 `**/CLAUDE.md` 是冗余条目。

**建议替代方案**：
- 在最终方案中直接删除 §4 的「改造 paths」代码块，只保留「保持不变」结论。避免执行者误读。

## 反对意见 6：`read-before-write.md` 新增 `*.js` 的实际收益存疑

**反驳点**：《rules-改造方案.md》第一节 §1 提议新增 `services/**/*.js`。

**具体质疑**：

- 理由是「前端构建脚本为 JS」。但本项目前端使用 Vue3 + Vite，构建配置文件是 `vite.config.ts`（TypeScript），已被 `services/**/*.ts` 覆盖。
- `services/` 下的 `.js` 文件主要是 `node_modules/` 中的依赖（方案自身在 §4.1 风险自检中承认了这一点）和可能的编译产物。编辑这些文件的场景极为罕见。
- 方案的风险自检标注「node_modules/ 下 JS（极低概率）」，但未考虑 `.js` 文件在 `services/live-crawler/monitor/frontend/` 下可能存在的编译产物或第三方脚本。

**援引依据**：《方法论摘要.md》第 a 条「具体扩展名优先」+ 反例条款 3 的精神——新增 glob 应有明确的触发场景和收益。如果无法举出一个具体的 `.js` 文件编辑场景需要先读 CLAUDE.md，则不应新增。

**建议替代方案**：
- 不新增 `services/**/*.js`。
- 如果确有前端 JS 文件需要覆盖，使用更精确的路径：`services/*/monitor/frontend/src/**/*.js`。

## 反对意见 7：整顿方案的「未决项」设计暴露了方案本身的不确定性

**反驳点**：《整顿方案.md》第六节「未决项」列出了 3 个待用户决策项和 2 个争议点。

**具体质疑**：

- 一个「整顿方案」如果有 5 个未决项，说明方案尚未成熟到可执行阶段。特别是争议点 1（PRD 归 specs 还是 designs）和争议点 2（DDD 归 designs 还是 specs）直接影响文件移动目标路径。如果用户选择了方案推荐之外的选项，移动清单需要重写。
- 这不是方案的问题，而是执行时序的问题：应先解决未决项，再交付移动清单。当前方案将「未决定」和「已决定」混在一个文档中，增加了执行者的认知负担。

**援引依据**：《方法论摘要.md》第 e 条「程序化校验 vs 自然语言约束的决策矩阵」中强调「确定性规则程序化」。文件移动是确定性操作，其前提条件（目标路径）也应是确定的。将不确定性留在确定性操作的方案中，是设计缺陷。

**建议替代方案**：
- 将未决项从方案正文中提取为独立的「待决策清单」，由 team-lead 先行确认。
- 方案正文仅保留已确定的移动清单，消除执行歧义。

## 1. 产品概述

### 1.1 产品定位

Live Platform 是一个面向跨境电商直播业务的**数据采集基础设施**，为派大星系统提供准确、实时的直播 GMV 数据支持，解放人工录入，提升数据时效性和准确性。

### 1.2 核心价值主张

**解放双手，再也无需招聘专门的实习生去录入各国家每日的数据；提高了数据时效性，辅助 BU 快速进行日度 PDCA；提高了数据的准确性，减少人为少录、错录导致的成本增加。**

### 1.3 业务背景

Livelab 主营业务围绕直播展开，每日产生大量的 GMV 数据。0331 前仍需手动录入三大渠道（TikTok、Shopee、Lazada）的 GMV 数据到 BPMS，才能计算对应业绩；BU 较难获取到准确的日度数据进行 PDCA，存在**耗时耗力、准确性低、时效性低**的痛点。

### 1.4 业务规模

- **TikTok**：160 个账号（核心平台）
- **Shopee**：60 个账号
- **Lazada**：5 个账号（新上线）

## 2. 用户与场景

### 2.1 目标用户

| 用户角色 | 使用频率 | 核心诉求 |
|---------|---------|---------|
| **爬虫采集工程师** | 每日多次 | 监控采集运行健康、排查异常、补采数据 |
| **数据团队** | 每日查看 | 确认今日数据完整性报告是否可用 |
| **BU 业务方** | 偶尔查看 | 了解直播间开播状态、数据采集进度 |

### 2.2 核心场景

#### 场景 1：录入直播间并监控开播

**角色：** BU 业务方  
**触发：** 新增直播间需要监控  
**流程：**
1. 用户在派大星系统录入直播间地址
2. 派大星调用 live-monitor API 获取直播间信息
3. live-monitor 开始监控该直播间是否开播
4. 检测到开播后（1分钟内），live-stream 自动拉取视频流
5. 视频流切割后推送到 OSS（防摸鱼）

**预期结果：** 直播间开播后 1 分钟内开始录制视频

#### 场景 2：用户登录授权

**角色：** BU 业务方  
**触发：** 需要采集某账号的商家后台数据  
**流程：**
1. 用户在派大星系统发起登录请求
2. adspower-server 创建浏览器环境并返回投屏 URL
3. 用户通过投屏界面手动登录
4. adspower-server 检测到登录成功，回调派大星系统
5. live-crawler 开始采集该账号数据

**预期结果：** 登录成功后立即开始数据采集

#### 场景 3：实时 GMV 数据采集

**角色：** 系统自动  
**触发：** 定时任务（5分钟）  
**流程：**
1. live-crawler 定时任务触发
2. 查询正在直播的账号列表
3. 执行双轨采集（TikTok/Shopee 浏览器，Lazada HTTP）
4. 采集到的原始数据推送到 Kafka
5. 数据仓库消费 Kafka 消息，清洗后推送到派大星系统

**预期结果：** 5 分钟内完成一轮实时采集

#### 场景 4：监控采集运行健康

**角色：** 爬虫采集工程师  
**触发：** 每日例行检查  
**流程：**
1. 工程师打开监控系统首页
2. 查看最近 30 分钟各国家各平台的运行健康
3. 发现某平台成功率下降，点击进入详情页
4. 查看异常账号列表和异常原因
5. 执行补采或排查问题

**预期结果：** 快速定位异常账号和原因

#### 场景 5：确认今日数据完整性

**角色：** 数据团队  
**触发：** 每日下午确认数据是否可交付  
**流程：**
1. 数据团队打开监控系统首页
2. 查看今日完整性报告就绪度
3. 确认各国家各平台是否达到"已就绪"状态
4. 如有风险或阻塞，查看缺失数据集和受影响账号
5. 通知工程师补采

**预期结果：** 明确知道今日数据是否可用

## 4. 功能需求

### 4.1 直播间监控 (live-monitor)

#### 4.1.1 核心功能

| 功能 | 优先级 | 说明 |
|------|--------|------|
| 直播间录入 | P0 | 接收派大星系统录入的直播间地址 |
| 开播检测 | P0 | 1分钟内检测到直播间开播 |
| 房间分配 | P0 | 将开播房间分配给 live-stream |
| 主备高可用 | P0 | 主节点故障 30 秒内切换到备节点 |
| 房间状态管理 | P0 | 管理直播间生命周期状态 |

#### 4.1.2 API 接口

| 接口 | 方法 | 说明 |
|------|------|------|
| `/liveRoom/portInfo` | POST | 获取 TikTok 直播间信息 |
| `/liveRoom/shopeeInfo` | POST | 获取 Shopee 直播间信息 |
| `/liveRoom/lazadaInfo` | POST | 获取 Lazada 直播间信息 |
| `/get_roominfo` | POST | live-stream 获取可用房间 |
| `/report_roominfo` | POST | live-stream 上报房间状态 |
| `/health` | GET | 健康检查（主备切换用） |

### 4.2 视频流录制 (live-stream)

#### 4.2.1 核心功能

| 功能 | 优先级 | 说明 |
|------|--------|------|
| FFmpeg 推流 | P0 | 拉取直播流并录制视频 |
| 断流重连 | P0 | 智能重连机制，最多 10 次 |
| 视频切割 | P0 | 8 秒分段切割 |
| OSS 上传 | P0 | 切割后自动上传到 OSS |
| Kafka 通知 | P0 | 上传成功后推送消息 |
| 流状态监控 | P1 | 实时监控流健康状态 |

#### 4.2.2 性能指标

| 指标 | 目标值 |
|------|--------|
| 断流重连时间 | < 5 秒 |
| 视频分段时长 | 8 秒 |
| 上传成功率 | > 95% |
| 最大重连次数 | 10 次 |

### 4.3 浏览器管理 (adspower-server)

#### 4.3.1 核心功能

| 功能 | 优先级 | 说明 |
|------|--------|------|
| 浏览器创建 | P0 | 创建 AdsPower 浏览器环境 |
| CDP 投屏 | P0 | WebSocket 实时投屏 |
| 登录监控 | P0 | 检测 TikTok/Shopee/Lazada 登录状态 |
| 登录回调 | P0 | 登录成功/失败回调派大星系统 |
| 浏览器关闭 | P0 | 关闭浏览器环境 |

#### 4.3.2 API 接口

| 接口 | 方法 | 说明 |
|------|------|------|
| `/api/browser/profile/create` | POST | 创建并启动浏览器 |
| `/api/browser/profile/close` | POST | 关闭浏览器 |
| `/ws/remote/{session_id}` | WebSocket | 投屏双向通信 |

### 4.4 数据采集 (live-crawler)

#### 4.4.1 核心功能

| 功能 | 优先级 | 说明 |
|------|--------|------|
| 双轨采集 | P0 | 浏览器（TikTok/Shopee）+ HTTP（Lazada） |
| 实时采集 | P0 | 5 分钟采集正在直播的场次 |
| 历史采集 | P0 | 每日全量采集 |
| 数据上报 | P0 | Kafka 推送原始数据 |
| 养号服务 | P0 | Cookie 定时刷新 |
| 采集完整性监控 | P1 | SQLite 记录采集事件 |

#### 4.4.2 采集模式

| 模式 | 触发条件 | 说明 |
|------|---------|------|
| 全量采集 | 新账号 / 登出恢复 | 采集所有历史数据 |
| 增量采集 | 正常状态 | 只采集最新数据 |
| 实时采集 | 定时任务（5分钟） | 只采集正在直播的场次 |

## 5. 统一监控系统

### 5.1 产品定位

**爬虫采集工程师的国家级采集驾驶舱 + 数据采集完整性报告工具**

### 5.2 核心问题

1. 最近 15/30/60 分钟，当前国家与平台的采集运行是否健康？
2. 今天这份"数据采集完整性报告"是否已经达到可查看、可交付的状态？

### 5.3 首页设计

```
国家级采集驾驶舱
├─ 顶部过滤
│  ├─ 日期：默认今天
│  ├─ 时间窗口：15 / 30 / 60 分钟
│  └─ 国家筛选：全部 / 指定国家
├─ 上半区：最近窗口运行健康
│  └─ 国家卡片
│     ├─ TikTok 平台块
│     │  ├─ 成功率
│     │  ├─ P95 耗时
│     │  ├─ 异常账号数
│     │  └─ 最近异常时间
│     ├─ Shopee 平台块
│     └─ Lazada 平台块
└─ 下半区：今日完整性报告就绪度
   └─ 国家卡片
      ├─ TikTok 平台块
      │  ├─ 状态：已就绪 / 有风险 / 已阻塞
      │  ├─ 缺失数据集数
      │  └─ 受影响账号数
      ├─ Shopee 平台块
      └─ Lazada 平台块
```

### 5.4 监控指标定义

#### 5.4.1 运行健康指标

| 指标 | 定义 | 阈值 |
|------|------|------|
| 成功率 | 窗口内 success 次数 / 总次数 | 绿色 ≥95%，黄色 ≥80%，红色 <80% |
| P95 耗时 | 窗口内 95 分位耗时 | - |
| 异常账号数 | 窗口内出现非 success 的账号数 | - |
| 最近异常时间 | 窗口内最后一条异常记录时间 | - |

#### 5.4.2 报告就绪度指标

| 状态 | 定义 |
|------|------|
| 已就绪 | 所有关键数据集覆盖率 ≥95% |
| 有风险 | 所有关键数据集覆盖率 ≥80%，且至少一个 <95% |
| 已阻塞 | 任一关键数据集覆盖率 <80% |

### 5.5 统一数据集模型

| dataset_key | 用途 | 说明 |
|-------------|------|------|
| `realtime_account_snapshot` | 运行健康 | 实时账号级摘要 |
| `realtime_room_catalog` | 运行健康 | 实时直播间清单 |
| `realtime_room_core` | 运行健康 | 实时直播间核心详情 |
| `report_room_catalog` | 报告就绪 | 今日直播间清单 |
| `report_daily_summary` | 报告就绪 | 日级汇总 |
| `report_room_core` | 报告就绪 | 场次级核心指标 |

## 7. 数据流

### 7.1 端到端数据流

```
派大星系统录入直播间
    ↓
live-monitor 监控开播
    ↓
live-stream 拉取视频流 → OSS 存储 → Kafka 通知
    ↓
用户登录授权（adspower-server）
    ↓
live-crawler 采集 GMV 数据 → Kafka 推送
    ↓
数据仓库消费 Kafka → 清洗计算
    ↓
派大星系统展示数据
```

### 7.2 Kafka Topic 设计

| Topic | 生产者 | 消费者 | 说明 |
|-------|--------|--------|------|
| `liveTs` | live-stream | 数据仓库 | 视频切片上传通知 |
| `streamer_lazada_relate_data` | live-crawler | 数据仓库 | Lazada 采集数据 |
| `streamer_tiktok_relate_data` | live-crawler | 数据仓库 | TikTok 采集数据 |
| `streamer_shopee_relate_data` | live-crawler | 数据仓库 | Shopee 采集数据 |

## 8. 重构优先级

### 8.1 P0 - 核心稳定性（1-2周）

1. **修复 live-stream 断流问题**
   - 优化 FFmpeg 参数（重连、超时、缓冲）
   - 增强重连机制（指数退避、健康检查）
   - 添加流状态监控（心跳检测）

2. **重构 live-monitor + live-stream 整合**
   - 统一直播间状态管理
   - 清晰的 API 接口
   - 开播检测 → 自动拉流 → 视频切割 → OSS 上传

### 8.2 P1 - 监控系统（1周）

1. **实现国家级采集驾驶舱 MVP**
   - 国家 -> 平台 -> 账号三层视角
   - 实时运行健康 + 今日报告就绪度
   - 统一数据集模型

### 8.3 P2 - 架构优化（后续）

1. **live-crawler 改为纯 API + 养号服务**
   - 拆分为独立的养号服务
   - 纯 HTTP API 采集（去除浏览器依赖）

2. **完善监控系统**
   - 开播历史统计
   - 告警通知（钉钉/邮件）
